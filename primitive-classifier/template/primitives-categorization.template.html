Acme primitives audit, what belongs where

Anthropic ships six primitives. Each has one job. The Acme stack today routes most static "how do I do X" content through the platform-guidelines MCP server. That worked when MCP was the only tool in the box. It is no longer. This page categorizes every Acme skill and every MCP tool into the primitive that actually fits, with the reasoning behind each call.

Sources: platform-skills/acme/skills/ (19 skills), platform-guidelines-mcp-server/ (75 guideline files, 93 BCCs, 85 OpenAPI specs), governance architecture deck and companion.

The headline

Four things to walk away with.

Static content is delivered through MCP, the tool stays but its scope shrinks

About 62 of 75 guidelines in the MCP server are pure procedural knowledge ("how do I write a hexagonal adapter," "what's our git commit format," "how do we name things"). These are the canonical skill shape: files in git, loaded on demand. The MCP tool that serves them (get-guideline) is fine as a primitive, but its scope shrinks: 62 of 75 type values disappear because the underlying files move into the skill marketplace. We call this kind of issue a reshape in place (right primitive, wrong scope).

A few guidelines do belong in MCP, the live ones

Team contacts, infrastructure permissions, release calendar, test customer DBs, dashboard URLs, OpenAPI specs, BCCs all change on a business cadence. These are connectivity, the textbook MCP use case. Keep them. Sharpen the server's scope to just these.

Hooks and settings.json are absent, the enforcement floor is missing

Acme uses settings.json minimally and uses no PreToolUse / PostToolUse hooks. Iron laws like "no @Transactional in application/" are advisory text in skills today. These should be deterministic, blocked at the tool boundary, not advisory in markdown.

This audit is grounded in Anthropic docs, where we extrapolate is flagged

Each item below carries a provenance badge: doc'd (verbatim Anthropic guidance), inferred (a defensible reading the docs do not say literally), or org (org context, not Anthropic's call). The decision framework and source list make every claim traceable to a URL.

The migration shape

Reading the audit as a sequence: what to do, in what order.

Phase 1, prove the model on one skill (this quarter)

  1. Migrate ddd-patterns (66 lines, lowest-rated, called out by name on slide 13). Pull the body of domain-service-guidelines.md and architecture-guidelines.md from MCP into the skill body. Target ~150 lines, half of backend-story's size.
  2. Add an ArchUnit verification step as a hook on PostToolUse for any Edit / Write under **/model/**. The skill's iron law ("no framework annotations in domain") becomes deterministic.
  3. Measure: regression eval pass rate at CI, time-to-update for a guideline, onboarding time for a new dev reading the skill cold.

Phase 2, sharpen what stays in MCP

  • Keep: get-openapi-spec, search-openapi-specs, list-openapi-services, all BCC tools, get-guideline type=team, type=infrastructure, type=release-planning-2026, type=billing-test-customer-search, dashboard / dynatrace / kibana lookups.
  • Remove from MCP (move into git as skills or skill bodies): the ~62 procedural guidelines. That is the bulk of slide 12's audit.
  • Any skill that previously called get-guideline type=X for a now-skill-bodied guideline gets the content inlined. The skill body becomes the source of truth.

Phase 3, add the missing primitives

  • Hooks: ArchUnit on domain edits, SonarQube blockers on commit, PII regex on analytics edits, "no Slack" lint on docs (Acme uses Teams, currently a markdown comment in two skills, should be a deterministic check).
  • settings.json: permissions.deny for dangerous bash patterns, permissions.allow for the trusted MCP tools, environment variable bindings.
  • Subagents: the compliance agents already mentioned in backend-story (test-quality-guardian, java-client-service-guardian, security-scanner) get formal subagent files in .claude/agents/, with deterministic tool allowlists.
